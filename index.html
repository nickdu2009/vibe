Cursor / Claude Code / Codex 已经使用一段时间了——但一个现实是："AI 写完代码，review 一下" 这句话已经不成立了。问题不只是看不完，而是看不完之后，如何保证代码符合业务意图？

02 The Shift

一个症状 · 一个目标 · 三段控制 + 判断外置

承认 A · 在 coding 上，AI 擅长输入边界清楚、代码模式可复用、反馈能自动验证的任务——仿写既有结构、boilerplate、字段映射、接口适配、测试和 migration，通常更快也更稳。
承认 B · 而且 AI 代码产出已经超过 review 带宽——一旦需求进入多轮讨论、多 Agent 协作和长会话，"写完代码再 review 一下"这件事在物理上做不到了。
目标 · 在 AI 高速写代码时，仍然保证业务正确性——把业务意图注入流程，把业务判断留在会话之外，把正确性变成可执行检查。

03 Q1 · 角色

问题 ❶ · 业务意图怎么注入？→ 事前声明

核心转变：业务意图注入，不是“把需求说清楚”这么泛；而是把 AI 无法从代码里可靠推断的业务判断，提前变成任务输入。

① 业务规则

什么情况下成功 / 失败 / 跳过 / 报错。
例：origin_form 缺字段就直接失败。

② 系统契约

接口行为、字段来源、兼容边界不能被改。
例：不回退 policy.Premium，旧 toko contract 不动。

③ 不变量

无论怎么实现都必须成立的约束。
例：toko / toko-pro 不能串源，其它不变。

④ 必做 / 禁止项

哪些行为必须保留，哪些“优化”不能出现。
例：配置中的邮件都要发送；不能增加猜测式 fallback。

⑤ 验收标准

什么证据算完成，而不是“代码写了”。
例：哪些测试、golden case、真实链路和证据包必须通过。

规律：AI 能学到代码结构，但业务判断必须在任务输入中显式声明。载体可以是 Task brief / Plan / AGENTS.md / worktrail context / Skill / Validator，原则是：动手前能看到，动手后会被检查。
04 事中 · 控制面

事中怎么控？让 AI 持续暴露业务假设

关键转变：事中不是盯着 AI 写代码，而是控制它的工作节奏：先暴露假设和影响面，再给计划，分阶段执行，每阶段用 review-loop 自检。

5 个事中控制动作

  • 列假设：字段来源、失败语义、fallback、兼容策略，哪些是 AI 猜的？
  • 查影响面：会不会动到旧接口、无关产品、报表、邮件、回调、下游通知？
  • 先给 plan：改哪些文件、为什么改、业务规则怎么落地、测试怎么证明。
  • 小步执行：一阶段只解决一个业务动作，阶段结束汇报保留了哪些不变量。
  • 暴露缺口：还没验证什么、哪些场景没覆盖、哪些风险需要进入 review gate。

这一步的目标不是让 AI 慢下来，而是让它不要带着隐藏业务假设一路写到底。

工具 · 5 种 review-loop

Loop事中要暴露的问题
requirements需求是否有二义性 / 缺失场景？
design方案是否破坏契约 / 不变量？
plan步骤、文件、验证是否可执行？
code实现是否偏离业务意图？
test正例、负例、链路、回归是否覆盖？

review-loop 是事中控制工具：让 AI 自己找问题、分类、修复，把隐藏假设摊开进入 review gate。

05 Q2 · 判断外置

问题 ❷ · 业务判断怎么不漂移？→ 判断外置

间接但关键：记忆管理本身不是业务正确性；但多轮对话、长会话、跨 Agent 协作时一旦丢掉业务判断，AI 就会写出业务不正确的代码。真正要保住的是为什么这样做、哪些不能改、哪些 fallback 被禁止、哪些风险没验证。
🔀

长会话会稀释判断

同一需求聊到第 20 轮，AI 仍记得文件结构，但很可能忘了为什么不能 fallback、为什么旧契约不能动。

📌

不漂移前提 · 判断外置

任何新会话 / 新 Agent 接手时，都能 3 分钟接住业务判断——靠 worktrail context / handoff，而不是翻聊天记录。

📊

外置的对象

不是保存所有上下文，而是保存业务规则、决策理由、禁止项、未验证风险、下一步验证。

⚡

外置的收益

AI 可以换会话、换工具、换 Agent；只要业务判断不丢，协作就不会退回“从头解释一遍”。

06 Q2 · 工具 + 实践

worktrail · 把业务判断留在会话之外

4 个原语

  • Context Pack · 任务开始第一步：worktrail context "task" → 自动注入当前业务判断 / 约束 / 下一步
  • State Capsule · 长任务 checkpoint，保留阶段性业务判断和未验证风险
  • Handoff Candidate · 结束或交接前留一份"为什么这么走、接下来怎么走"的草稿
  • Knowledge Lifecycle · import → distill → review → promote

硬约束 · 机制可追溯

  • 无 daemon · 无向量库 · 无内嵌 LLM
  • 所有真相在 Markdown + JSON 文件里 · git 友好
  • SQLite 只做索引 · 删了 index 重建即可

07 Judgment Trace

业务判断外置链路 · 同一需求跨多轮不漂移

业务判断外置不是保存聊天记录。它只抽取会影响业务正确性的东西：规则、契约、禁止项、决策理由、未验证风险和下一步验证。
08 Q3 · 治错

问题 ❸ · 事后怎么证明业务正确？→ Evidence-as-Authority

事后证明正确：不是把代码再 review 一遍，而是让候选实现通过业务门禁：契约能对上、不变量没破、关键案例能回归、真实链路跑得通、证据能留下。

AI 不会自动理解业务语义——它会用最像代码库的方式先猜。把 AI 输出永远当 Proposal。下面 3 个片段都不是语法错，而是业务语义需要被门禁固定下来：

① goto · 400103 错误码

澄清：「希望 tiktok/claims 返回 400103，其它不变」
AI v1：提议全局改错误码生成
追问：「partnerMeta 持久化了吗？」
AI v2：收窄到 TokoPro 入口 + partnerMeta
→ 通过持久化和影响面追问，收窄实现范围

② template-unify · 派生续保

AI v1：用 application.form + 多种 JSON shape 兼容
澄清：「去掉所有这样的兼容，origin_form 缺字段就直接失败」
AI v2：改 typed meta struct，硬失败
→ 移除「聪明 fallback」，强制确定性契约

③ consumer-finance · 报表保费

AI v1：优先 meta.tms_premium，旧数据 fallback policy.Premium
澄清：「不回退 policy.Premium」
AI v2：严格依赖 tms_premium，发现 config 生成器漏映射
→ 明确业务语义 + 暴露隐藏 bug

共同模式：AI 第一版 = 技术上 reasonable + 业务上暗藏假设。要保证业务正确性，澄清必须进一步沉淀成 validator / golden case / 不变量检查，而不是停留在一次对话里。
09 Q3 · 工具 + 实践

业务正确性的 5 道门禁 · 外加失败沉淀

AI 交付的是 候选实现。候选能不能进入主干，不靠“已经 review 过”，靠下面 5 类证据是否足够。

① 契约门禁

API 入参/出参、必填字段、字段来源、旧接口兼容边界、不允许的 fallback。
例：meta.tms_premium 缺失时不能回退 policy.Premium。

② 不变量门禁

绝对不能错的业务约束写成脚本/测试。
例：toko / toko-pro 不能串源，HMAC 必填，加密字段不能明文落库。

③ Golden Case 回归

固定输入 + 期望输出，验证业务语义不漂移。
例：prompt / parser / mapping 改动后，COI 字段抽取和 PromptSpeed 报表都要跑 golden。

④ 真实链路集成测试

不要只测函数，要测业务闭环。
例：API request → DB → webhook/callback → 邮件/日报；AI 输出 → validator → 最终渲染。

⑤ 交付证据包

AI 完成后必须交代：改了哪些业务规则、保持了哪些不变量、跑过哪些门禁、还有哪些风险没覆盖。

关键转变：review gate 从“逐行看代码”变成“判断证据是否足够”。每次 AI 猜错业务，不只修代码；要把错误沉淀成 validator、golden case、集成测试或 AGENTS/Skill 规则。

一个症状 · 一个目标 · 三段控制 + 判断外置

14 Anti-patterns + Actions

反例库 + 6 个可执行动作

下面 6 个坑都有同一个内核：AI 很容易写出"能跑但业务不对"的代码。一旦把"review 一下"当作兜底，业务正确性就已经开始失控。

⚠️ 反例库 · 业务正确性最容易失守的 6 坑

  • AI Merge 会丢方法——能编译不代表链路完整，关键路径必须有回归门禁（真实 commit fix: restore lost methods）
  • AI 爱给「聪明 fallback」——fallback 看起来稳，可能直接改变业务语义（"不回退 policy.Premium"）
  • "修 bug" ≠ "理解需求"——AI 想删配置时，要回到业务规则：配置中的邮件都要发送
  • 测试覆盖"焦点过窄"——AI 倾向为当前 feature 写 focused 测试，覆盖矩阵需要靠 test-review-loop 自检
  • Skill 不是越多越好——14 个 Skill 已是上限，"最多 4 个活跃"；太多规则会让 AI 抓不到真正业务约束
  • 「Plan 看起来完美」≠「可执行」——AI 写的 Plan 必须用真实仓库、真实契约、真实测试校验，不能用看的

✓ 6 个可执行动作

  • ① 给当前高频协作代码库写 AGENTS.md——把业务规则、系统契约、不变量、必做/禁止项、验收标准写进去，3 小时内一版
  • ② 任务开始前先 worktrail context，结束前 handoff——把业务判断、决策理由、禁止项和未验证风险留在会话之外
  • ③ 要求 AI 在 plan 前列业务假设和影响面——字段来源、fallback、兼容策略、旧接口、报表、邮件、回调都要先摊开
  • ④ 把 1 个事中控制动作写成 Skill——例如“先列业务假设 / 影响面 / 验证缺口”，让 AI 每次实现前自动暴露
  • ⑤ 给 1 条关键链路补业务门禁——从契约、不变量、Golden Case、真实链路里任选一类，先把最怕错的场景自动化
  • ⑥ 要求 AI 交付证据包——每次完成后列出业务规则变更、不变量、跑过的门禁、未覆盖风险；review gate 先判断证据是否足够
三段控制 · 判断外置

AI 高速写代码不是问题，业务正确性失控才是问题。

① 事前：把业务规则 / 契约 / 不变量 / 必做项注入给 AI，不再逐行兜底。
② 事中：让 AI 持续暴露假设 / 影响面 / 计划 / 阶段结果 / 验证缺口。
